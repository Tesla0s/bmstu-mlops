# Четыре дефекта части A

## 1. Несколько конфигураций записывались в один run

В заготовке цикл кандидатов находился внутри одного дочернего all-candidates.
Параметры фиксировались только при первом вызове; следующие кривые и веса смешивались.
Теперь start_run расположен внутри цикла: один родитель и шесть отдельных дочерних runs.
Фактическое доказательство: [снимок](../reports/mlflow-runs.json) содержит шесть FINISHED,
каждый с собственными r/lr/target_modules, четырьмя train-точками и val на 0, 2, 4.
Их base_val_loss одинаков: 0.783062721.

## 2. Файлы MLflow исчезали при замене контейнера

PostgreSQL уже имел volume, но каталог /mlartifacts находился в слое контейнера.
Добавлено именованное хранилище artifacts:/mlartifacts. Метаданные и файлы сохраняются отдельно.
Штатный make check-storage действительно заменил контейнер через --force-recreate;
идентификаторы до/после различаются: [проверка](../reports/container-recreation.json).
Затем скачан тот же probe-файл; SHA-256 fc5db5c95dbba9b40474b7cd540d36e56277f6596fcd7bdca3896bd7a1c99149.
Run хранения: [c15d107f093f4a6aacf49f18747144a0](http://127.0.0.1:5006/#/experiments/1/runs/c15d107f093f4a6aacf49f18747144a0).
Выполнялся не просто restart; volumes не удалялись.

## 3. Из происхождения удалялись версии train/val

provenance вычислял контрольные суммы, но src.sweep удалял все ключи data_*.
Фильтр убран. Все шесть runs содержат одинаковые SHA-256 исходных тензоров,
код, конфиг, Git-коммит и точную ревизию базы. Тензоры совпадают с ДЗ 4.
Полный индекс 1315 исходных вопросов связан с train через input_sha256 тензора
и совпадение всех id в исходном порядке: [происхождение](../reports/data-lineage.json).
Первый коммит обучения: 83ca05425d3f65bc2bb83c1b68868150e116f65c; git_dirty=False.
Исправление размещения DVC-описаний не меняет код, конфиг или тензоры выполненных runs.

## 4. Вычисление отношения loss не запрещало регистрацию

promote вычислял val/base, но не вызывал проверку gate до register_model.
Теперь gate вызывается первой: проверяет FINISHED, конечность, допустимость loss
и max_val_ratio. Никакой записи в реестр до успешной проверки нет.
Фактический кандидат: отношение 0.460129 при пороге 1.0.
Исходная проверка №6 требует отказа при пороге 0.0; дополнительные тесты
также проверяют отсутствие вызова register_model при отказе, NaN и отрицательном пороге.
Полный допуск по ответам выполняется отдельно: make promote повторно проверяет
сохранённые raw-ответы, протокол и метрики, затем назначает champion.

## Дополнительные изменения для этого проекта

- Собственная тема GitHub, фиксированные 32/8 id со всеми тремя классами.
  Первые строки исходных файлов были только question; их слепое использование исказило бы сравнение.
- Точные версии torch 2.8.0 / transformers 4.57.6 / peft 0.17.1 взяты из
  проверенного окружения ДЗ 5, остальные зависимости закреплены uv.lock.
- На MPS использовано обычное вычисление внимания eager; при генерации явно
  отключено наследование настроек случайного выбора из конфигурации базы.
- Полный пакет включает tokenizer, шаблон диалога, manifest и закреплённую базу.
  Сигнатура и пример входа явно передаются MLflow; загрузка не читает params.yaml.
- Реализованы две функции оценки; дополнительные тесты лежат в checks/.
  Каталог tests/ преподавателя не изменён: ожидаемый отпечаток c42ac7788026.
