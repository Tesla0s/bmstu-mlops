# Тема проекта: классификация обращений на GitHub

**Статус: предложена к согласованию с преподавателем.**
Это план следующих домашних работ: набор данных ещё не собран,
дообучение и оценка качества ещё не выполнялись.

## Задача

Модель читает заголовок и описание обращения в программном проекте
и предлагает категорию, чтобы помочь разработчику при первичном разборе.

| Категория | Смысл |
|---|---|
| `bug` | Сообщение о неправильной работе существующей функции |
| `feature_request` | Предложение новой функции или улучшения |
| `question` | Вопрос об использовании программы |

Вход — текст на английском языке. Выход — короткий JSON с одной категорией.
Иллюстративный пример, составленный для объяснения формата:

```text
Title: Application crashes when opening an empty file
Body: Opening an empty file closes the application without an error message.
```

```json
{"category": "bug"}
```

## Данные

**Планируемый объём — около 3000 обращений, примерно по 1000 на категорию.**
Данные собираются самостоятельно через публичный интерфейс GitHub (API).
Источники — [VS Code](https://github.com/microsoft/vscode/issues)
и [pandas](https://github.com/pandas-dev/pandas/issues).
Существующие метки сопровождающих проекта задают первоначальную разметку:

| Источник | `bug` | `feature_request` | `question` |
|---|---|---|---|
| `microsoft/vscode` | `bug` | `feature-request` | `*question` |
| `pandas-dev/pandas` | `Bug` | `Enhancement` | `Usage Question` |

Предварительная проверка публичного API 5 сентября 2026 года подтвердила
наличие всех шести сочетаний проекта и категории. Это проверка доступности
источников; итоговый размер набора будет известен после сбора и очистки.

Для каждого примера сохраняются ссылка, проект, номер обращения, дата создания,
дата получения и исходные метки. Модель получает только очищенный заголовок
и описание; служебные поля и метки не входят во входной текст.

Очистка исключает предложения изменения кода (`pull_request`), пустые обращения,
сообщения ботов и случаи с несколькими целевыми категориями. Удаляются
повторы, почти одинаковые тексты, шаблонные подсказки категории и префиксы
вроде `[BUG]`. Обычные содержательные слова в тексте сохраняются.
Длинные сообщения ограничиваются по длине после очистки; примеры, потерявшие
существенное описание проблемы, исключаются.

Планируется вручную проверить не менее 90 примеров, по 30 на категорию,
до начала экспериментов: метки GitHub могут быть неполными или ошибочными.
Окончательные правила очистки и число исключённых записей фиксируются в отчёте.

## Проверка качества

После удаления повторов обращения делятся по времени создания внутри каждого
проекта: около 70% на обучение, 15% на подбор настроек и 15% на итоговую проверку.
Более новые обращения попадают в итоговую часть. Состав частей сохраняется;
одинаковые и почти одинаковые тексты не должны попадать в разные части.
Итоговая часть не используется для выбора модели и её настроек.

Основная метрика — **macro-F1**: для каждой категории рассчитывается F1,
объединяющая точность и полноту, затем три значения усредняются с равным весом.
Дополнительно проверяются качество каждой категории, таблица перепутанных
категорий и доля ответов в правильном формате JSON. Неверный формат считается
ошибкой, такие ответы не исключаются из подсчёта качества.

Сравниваются исходная Qwen3-0.6B, модель после дообучения и простой классификатор
по частотам слов (TF-IDF и логистическая регрессия). Превосходство языковой
модели заранее не предполагается. Результат относится к новым обращениям
в выбранных проектах; переносимость на другие проекты отдельно не доказана.

## Обучение и ресурсы

Используется базовая модель курса **Qwen/Qwen3-0.6B**. При дообучении основные
веса фиксируются, а обучаются небольшие добавленные матрицы — адаптеры LoRA.
Основная модель всё равно участвует в вычислениях на каждом шаге.

**Основной вариант — бесплатная видеокарта в Kaggle.** На Mac выполняются
подготовка данных, разработка и запуск модели. Локальное дообучение на
Apple M3 Pro с 36 ГиБ памяти рассматривается как запасной вариант после замера.
Платные API моделей, подписки и аренда видеокарт в план не входят.

Начальная конфигурация для будущего эксперимента: LoRA с рангом 8,
не более 512 токенов на полный обучающий пример и один пример за шаг.
Сначала выполняются 20–50 пробных шагов, измеряются память и время;
по ним выбираются объём обучения и число проходов по данным.
Формат вычислений выбирается с учётом доступной видеокарты.
Время и память дообучения пока не измерены; скорость генерации из ДЗ 1
не используется как оценка скорости обучения.

Kaggle предоставляет бесплатные видеокарты с недельной квотой;
доступность и остаток проверяются в аккаунте перед запуском.
При исчерпании квоты обучение продолжается после её восстановления
или локально после проверки времени и памяти дообучения. Промежуточные результаты сохраняются.

размеченных по трём категориям: ошибка, новая функция, вопрос.
