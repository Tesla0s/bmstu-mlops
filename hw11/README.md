## Подготовка

Нужны Docker/Colima, kind, kubectl, Helm, Python 3.12 и uv.
На Mac команды выполняются **из корня репозитория bmstu-mlops**.

    export HW11_WORKSPACE="$PWD/../hw11/workspace"
    export PATH="$HW11_WORKSPACE/bin:$PATH"
    export KUBECONFIG="$HW11_WORKSPACE/kubeconfig"
    export DOCKER_HOST="unix://$HOME/.colima/mlops-hw11/docker.sock"
    mkdir -p "$HW11_WORKSPACE"
    df -h .
    python3 hw11/scripts/install_tools.py
    colima start mlops-hw11 --cpu 4 --memory 6 --disk 12 --root-disk 8 --vm-type vz --runtime docker --activate=false
    kind create cluster --config hw11/kind.yaml --kubeconfig "$KUBECONFIG" \
      --image kindest/node:v1.34.0@sha256:7416a61b42b1662ca6ca89f02028ac133a309a2a30ba309614e8ec94d976dc5a
    docker build -t hw11-api:1.0.1 hw11
    kind load docker-image hw11-api:1.0.1 --name mlops-hw11
    helm upgrade --install hw11 hw11/chart --namespace hw11 --create-namespace
    kubectl apply -f hw11/clients.yaml -f hw11/monitoring/resources.yaml -f hw11/monitoring/metrics-server.yaml
    kubectl -n hw11 rollout status deployment/hw11-api --timeout=180s
    kubectl -n hw11 rollout status deployment/prometheus --timeout=180s
    kubectl -n hw11 rollout status deployment/grafana --timeout=180s
    kubectl top pods -n hw11
    uv venv hw11/.venv --python 3.12
    uv pip install --python hw11/.venv/bin/python --require-hashes -r hw11/requirements.lock
    uv pip install --python hw11/.venv/bin/python --require-hashes -r hw11/analysis.lock

Для lab.py исполняемые kubectl и helm должны находиться в
$HW11_WORKSPACE/bin. Файл kind.yaml задаёт локальный порт API 16443.
Существующий кластер повторно создавать не нужно. Восстановление конфигурации:

    kind export kubeconfig --name mlops-hw11 --kubeconfig "$KUBECONFIG"

Prometheus открывается отдельной командой, которая остаётся работающей:

    kubectl -n hw11 port-forward service/prometheus 19090:9090 --address 127.0.0.1

Для просмотра Grafana в другом терминале:

    kubectl -n hw11 port-forward service/grafana 13000:3000 --address 127.0.0.1

Дашборд: http://127.0.0.1:13000/d/hw11. Анонимный доступ — только на чтение.
Параметр --kubelet-insecure-tls относится к сертификату kubelet локального kind.
Это настройка учебного кластера, а не рекомендация для рабочей инфраструктуры.

## Воспроизведение

Скрипты выполняются из корня репозитория. Используйте отдельную рабочую копию
для новых прогонов: они записывают одноимённые каталоги results.
A, B и C выполняются **последовательно**, иначе нагрузки будут мешать друг другу.

    hw11/.venv/bin/python -u hw11/scripts/experiment_b.py
    hw11/.venv/bin/python hw11/scripts/recover_metrics.py
    hw11/.venv/bin/python -u hw11/scripts/experiment_a.py
    hw11/.venv/bin/python -u hw11/scripts/experiment_c.py
    hw11/.venv/bin/python -u hw11/scripts/test_integration.py
    hw11/.venv/bin/python hw11/scripts/analyze.py
    hw11/.venv/bin/python hw11/scripts/build_report.py
    hw11/.venv/bin/python hw11/scripts/verify_evidence.py
    helm lint hw11/chart

B: 2 политики × 2 сценария × 3 повтора × 120 секунд — не менее 24 минут нагрузки.
Дополнительно нужны прогрев, сбор метрик и завершение очередей.
В C ожидается реальное уменьшение числа реплик.

Четыре клиента имеют разные IP. Генератор планирует новые запросы независимо
от завершения предыдущих. Keep-alive отключён; каждое соединение новое.
Автоматических повторов нет. Запланированное и фактическое время отправки
сохраняются отдельно. HTTPX ограничивает соединение и ожидание очередного чтения:
20–30 с в обычных опытах, 70 с для длительных потоков.

В B одинаковы расписание, 288 запросов, вход длиной 128 символов и пять частей
ответа. Хеш расписания записан в conditions.json. Кеш пуст перед каждым
прогоном; прогрев модели завершён заранее. Порядок политик меняется между повторами. Целевые 80% реализованы повторяющимся
расписанием 12 из 15 запросов; на конечном наборе это 231/288 = 80,21%.

Имитация кеша: до 16 хешей префикса, вытеснение давно не использованных.
Хранится только признак наличия, без текста другого диалога.
Попадание: 0,02 с CPU; промах: 0,16 с CPU; часть: 0,025 с CPU и пауза 0,1 с.
PBKDF2 выполняется до достижения заданного времени потока time.thread_time().
В C вычислительная стоимость умножена на шесть, пауза отключена.
Эти числа относятся к имитатору, не к настоящему движку языковой модели.

## Артефакт, прогрев и завершение

Обе версии небольшого файла модели находятся в ConfigMap. Процесс сверяет
SHA-256 файла, фиксирует загруженную версию и прогревается. Ошибка хеша
или намеренный сбой прогрева не допускают Pod к Service.

Проверка запуска ждёт загрузку и прогрев до 90 секунд. Проверка готовности
дополнительно учитывает вывод из обслуживания. Проверка жизнеспособности
проверяет HTTP-процесс. В исходном дефекте первые две ошибочно используют /health;
исправление возвращает их на /startup и /ready.

При штатном завершении снимается готовность, затем пять секунд отводятся
на распространение сетевых правил. Запросы, дошедшие в этот промежуток,
ещё обслуживаются. После этого Uvicorn закрывает вход и до 45 секунд завершает
активную работу. Общий предел завершения Pod — 60 секунд.
Отмена запроса не освобождает вычислительный слот раньше остановки CPU-работы.

## Измерения

Времена клиента — монотонные. TTFC = first_mono − sent_mono.
Интервалы между частями — разности соседних отметок; у N частей N−1 интервал.
Для одной части список интервалов пуст. Завершающая запись done не является
содержательной частью. Термины TTFT, TPOT и tokens/s для имитатора не используются.

p50/p95 считаются только по завершённым ответам и приводятся с числом наблюдений.
429, HTTP-ошибки, разрывы соединения, незавершённые потоки и тайм-ауты
сохраняются отдельно. Для успеха нужны HTTP 200, завершающая запись и
ожидаемое число частей.

Серверные гистограммы тоже учитывают только полностью завершённые ответы.
Для B сравниваются разности накопленных bucket-счётчиков на тихих границах.
Число серверных наблюдений должно совпасть с числом успешных клиентских ответов.
Точный PromQL сохранён. Различия p95 связаны с интерполяцией внутри bucket и
сетевой доставкой; равенство двух чисел не заявляется.

Request ID / session ID находятся в журнале и ответах, но не в метках Prometheus.
В одинаковых нагрузочных наборах request_id обозначает логический запрос;
полный ключ попытки — experiment/request_id. Анализ добавляет его как attempt_id
в сводный журнал и проверяет уникальность, сохраняя исходные записи без замены ID.
Метки исходов и кеша имеют конечный набор значений; имя Pod добавляется Kubernetes.
После аварийного завершения окончательный исход фиксируется клиентом, даже
если сервер не успел записать свой счётчик.

## Остановка и удаление

Остановить команды port-forward. Сохранить стенд для следующего запуска:

    colima stop mlops-hw11

Удалить только этот учебный кластер:

    kind delete cluster --name mlops-hw11

Полностью удалить отдельную виртуальную машину с её образами и томами:

    colima delete mlops-hw11 --force

Исходники и результаты в репозитории останутся. Другие профили и кластеры
этими командами не затрагиваются.

## Исправление запроса мониторинга

При проверке найдено, что обычное OR между running и waiting с одинаковыми
метками оставляло только левый ряд: PromQL при таком сопоставлении игнорирует
имя метрики. Выбор исправлен на один селектор по __name__. Исходный сбор
Prometheus был исправен, поэтому за все прогоны B выгружены исторические
ряды с шагом 2 с. Скрипт recover_metrics.py сохраняет исходные снимки,
ответ query_range и отдельно производную timeline-complete.jsonl.
В ней указаны источник и фактическое время вычисления значения. Ближайшая
предыдущая оценка отличается от времени снимка Kubernetes менее чем на 2 с.
Повторная выгрузка требует работающего Prometheus и сохранённого периода;
для обычного пересчёта приложенных результатов достаточно analyze.py.

Штатное обновление проверено для указанного профиля ответов. Более длинные
запросы требуют согласования пределов длительности и grace period; нулевая
доля обрывов для произвольной нагрузки не заявляется.
